## 解决记录

### TypeConverter（⚪ 不修复，一个都不补）

讨论结论：Go 无 `BigDecimal`/`BigInteger`/`Number` 对应类型，且金融精度已在**扫描层**无损解决——`db/executor.go` 扫描时非二进制列经 `bytesToStr`（`[]byte→string`）保留，`DECIMAL`/`NUMERIC` 不在 `isBinaryColumnType` 二进制清单内，故 `123456789.123456789` 出来仍是精确字符串，精度一点没丢。补 `ToDecimal` 要么引入第三方 `shopspring/decimal`（违反 db 模块零外部依赖），要么返回 `string`（而 string 已是原始料）。逐项裁决：

| 请求项 | 裁决 | 理由 |
|--------|------|------|
| `toBigDecimal` | 不补 | 无 Go 类型；精度已在扫描层无损；选 decimal 库是应用层决策 |
| `toBigInteger` | 不补 | DB BIGINT 恒落 int64（max 9.2×10¹⁸），int64 已覆盖 |
| `toNumber` | 不补 | Go 无 `Number` 接口/装箱，返回 `interface{}` 等于 no-op |
| `toShort`/`toFloat` | 不补 | int16/float32 为对称性，无实际缺口，价值低 |
| `toByte` | 不补 | uint8 静默截断 >255，是 footgun |

TypeConverter 维持现状 6 个（`ToInt/ToInt64/ToFloat64/ToBool/ToString/ToTime`）。

### 其余 7 项（🟢 已实现）

- **复合主键（任意列数）**：`db/dao.go` 新增 `FindByCompositeIds`/`DeleteByCompositeIds`（variadic ids）；`db.go` 新增同名顶层函数；`executor.go` 的 `execDeleteByCompositeId` 改用 `NewRow(table).SetPrimaryKeys(pks...)` 支持 N 列（find 路径本就支持），并加 keys/ids 数量一致性校验。
- **事务返回值 + 主动回滚**：`db/transaction.go` 新增泛型 `TransactionOf[R]`/`TransactionOfCtx[R]`/`TransactionOfWithID[R]`/`TransactionOfCtxWithID[R]`，返回泛型业务结果；`db.Tx` 控制句柄（`Rollback()`）支持成功路径主动回滚；`db.RollbackDecision` 接口（`ShouldRollback() bool`）让结果驱动回滚；`db.ErrRollback` 哨兵错误；`executor.go` 新增 `execTransactionOf` + Dao 层 `DaoTransactionOf[R]`（Go 不支持泛型方法，故为自由函数）。`server/tx_interceptor.go` 改用 `shouldRollbackOutput` 优先识别 `RollbackDecision`，回退 `Code()!=0`（`server.Out` 已实现 `ShouldRollback`）。
- **Kv**：新增 `db/kv.go`——`type Kv map[string]interface{}`（直接嵌入 map，string 键），可直接传 SqlKit（`db.Sql(sql, kv)`，无需 `.Map()`）；fluent `Set/SetMap/Unset/SetIfNotBlank/SetIfNotNull`、typed getters（`GetStr/GetInt/...` 及 Default 变体）、`Keep`、`Map()`、`KvAs[T]` 转换器。Go map 无序，故不保插入序、不排序。
- **Row 小缺口**：`SetOrPut`/`SetOrPutMap`（已存在→Set 跟踪变更，不存在→Put 不跟踪）、`Data()`/`SetData()` 批量读写、`RowAs[T]` 函数式转换器（nil 安全）。
- **SqlKit**：`operator.go` init 现按 `strings.ToLower(op.key)` 注册全小写别名（补 `notcontains/startswith/endswith` 等，对照 Java `createCache` 的 `toLowerCase`）；`orderby_directive.go` 在字面量字段、`sqlField:clientField` 映射、运行时 field/order 四处补 `strings.TrimSpace`（对照 Java `.trim()`）；`para_directive.go` 新增包级 `checkParaAssigned` 开关与 `SetCheckParaAssigned(bool)`，在 SetExprList 与 Exec 两处门控未赋值检查。
- **错误回调/默认值**：`dao.go` 新增 `FindOneWithMsg(func(int) string)`/`FindOneOrNullWithMsg`（按结果数生成错误消息）；`QueryFieldOr(def)` 默认值重载；`executor.go` 的 `execFindOne` 增 msgFn 参数。
- **Batch 补强**：`db/batch.go` 重写——`BatchResult` 增 `UpdateCounts`/`GeneratedKeys`；`Batch` 增 `BatchSize`/`CommitOnBatchSize`/`GetGeneratedKeys` 配置项；`commitOnBatchSize` **自管事务**（`beginForChunking`/`commitChunk`/`commitTail`，按 batchSize 提交并重开事务，末尾块一并提交，**不应外包 TransactionCtx**）；`getGeneratedKeys` 经 `sql.Result.LastInsertId()` 回填（驱动相关，MySQL/SQLite 支持）；新增异构批 `InsertGroup`/`UpdateGroup`，按 (table, 字段集[, 主键集]) 分组、各组独立 prepared statement。

### 遗留

- `commitOnBatchSize` 采用自管事务模型（batch 接管事务生命周期），与 Java“提交外层事务”语义略有差异——Go 的显式 ctx 传播下无法透明地提交外层事务，已在文档与注释中说明不应外包 `TransactionCtx`。
- `getGeneratedKeys` 依赖驱动 `LastInsertId()`，PostgreSQL 等需 `RETURNING` 的场景未覆盖（按需走 `Client.KgoClient` 式原生口子或后续扩展）。
