Solon-AI 迁移到 Go 的设计（ai）：总览 ​

本文是「Solon-AI 迁移到 Go」系列的第一篇（总览与可行性）。 配套：01-go-comparison.md（Java→Go 逐项对照）、02-chat-core.md（聊天模型核心）、03-agent-design.md（智能体与流编排）、04-mcp-design.md（MCP 协议）、05-rag-design.md（RAG 检索增强）、06-talents-and-extended.md（Talents/Sandbox/Harness/Loop/UI/ACP）、07-migration-plan.md（迁移步骤与分期路线）。 源码参照：/Users/airhead/WorkSpace/goldsyear/solon-ai（org.noear:solon-ai-framework 4.1.1，git tag 4.1.1）。 目标宿主：aifei-go 工作区（Go 1.27，多模块；核心模块零外部依赖）。

迁移状态（2026-10-11 全量收口）：P0–P4 主干、P5 全部立项项、以及 2026-10-11 解锁的全部按需项（team 协议 8/8、ragloader 7 格式、ragrepo 14 后端、talents 18/18、web crawler、agui agent 流、loop 集成桥、harness 压缩）均已落地——P5-T talents 五件、P5-S sandbox 四卡（darwin/linux/代理/windows）、P5-M（rerank/generate/agui/gemini-interactions/MCP×Talent 桥）、P5-R ragloader、P5-V ragrepo、P5-H harness、P5-L loop。DoD 六项验收全过（见 07-migration-plan.md §9）。明确不迁/缓迁项维持 §2.2 决策不变。

本文不写实现代码，只给出：solon-ai 是什么、迁什么不迁什么、概念词典、模块地图、关键设计决策、可行性结论——作为后续逐篇的契约。所有设计均为提案，供最终审核与逐步调整。

0. TL;DR（设计摘要） ​

  • solon-ai 是一个约 39 万行 Java 的全栈 AI 应用框架，分层清晰：solon-ai-core（聊天/嵌入模型抽象 + 消息/事件/工具/会话 + RAG SPI + Talent SPI，28.5K 行）→ 5 个厂商方言（33.4K 行）/ router → solon-ai-agent（Simple/ReAct/Team 智能体，构建在 solon-flow 之上，39.9K 行）→ solon-ai-flow（AI 流编排组件，2.1K 行）/ solon-ai-mcp + mcp-core（MCP 协议，35K 行）→ talents（18 个能力包，48.8K 行）→ harness / loop（Claude-Code 式编排容器与持久循环引擎，24K 行）；旁支：RAG 三件套（加载器/仓储/搜索，25K 行）、sandbox（10K 行）、ui 流式协议适配（6K 行）、ACP（20.8K 行）。
  • aifei-go 已具备最关键的前置依赖：./flow（solon-flow 的忠实 Go 移植，NamedTaskComponent/GraphSpec/Engine.Eval 与 Java 逐字对应，已核实）可直接承载 solon-ai-agent 的 TeamAgent 与 solon-ai-flow 的组件模型；./enjoy 对标 SnEL 表达式（角色模板渲染、RAG 过滤表达式）；./dami 对标 FlowContext 的 EventBus；./json/./log/./config/./server 各就其位；./plugins/elasticsearch 可直接作 RAG 仓储后端。solon-ai 中用到的 flow 能力可以直接复用，无需改 flow 的核心语义（仅一处可选增量：flow.Node 的 per-node 附件缓存，见 03）。
  • 最大的语言鸿沟是 Reactor：solon-ai 全线以 Flux<ChatEvent>/Mono 为公开 API（30 种聊天事件、流式工具递归、MCP/ACP 会话）。对策：context.Context 取代 Thread.interrupt 式取消；回调 Sink 为主契约（对齐方言层 ctx.emit() 推模型）+ <-chan ChatEvent 适配器为人体工学形态；事件模型的不变量（RESPONSE_START/END 各恰好一次、失败时 ERROR 事件与 error 返回双通道且无 RESPONSE_END、STEP 边界随工具递归递增）原样保留为 Go 契约。
  • nami 现状不满足流式：nami/channel/http 整包 io.ReadAll 后才交给 Decoder，Channel.Call 是请求/响应形状，且默认 30s 总超时会杀死长流。对策：./ai 自带一个约百行的轻量 HTTP+SSE 客户端缝（net/http，可注入 *http.Client），非流式与流式统一走它；nami 保持不动（见 6.2 决策 D2，含备选方案）。
  • 反射面用 Go 惯用法替换：@ToolMapping 方法注解 → reflect 扫描 + 参数 struct tag 生成 JSON Schema（server.Register / dami Lpc 已有同型先例）；@McpServerEndpoint → 注册式 API；CRTP 自类型泛型链（ModelOptionsAmend<T,X>）→ 每层一个具体 Options 类型 + 链式 setter。
  • MCP 自研而非套用官方 Go SDK：mcp-core 本就是 vendored 的官方 Java SDK fork；Go 侧按本仓库「自包含、零外部依赖」的一贯哲学（dami/flow/nami 先例）原生实现协议层（schema + JSON-RPC + 会话 + stdio/Streamable HTTP/SSE 传输），JSON 编解码 SPI 模块（mcp-json-jackson2）在 Go 中自然消失（encoding/json 即全集）。
  • 定位：新增 ./ai（核心，零外部依赖）+ ./mcp（协议库，零外部依赖）+ ./ai/agent、./ai/flow（编排层，依赖 ./flow）+ ./plugins/ai 系列（装配与带三方依赖的后端）；填补 aifei-go 在「LLM 应用 / 智能体编排 / 工具协议 / RAG」层的空白，与现有 flow（编排）、dami（事件）、nami（RPC）、db（持久化）互补成完整栈。
  • 工作量预估：P0–P4 核心路径（chat/流式/方言/agent/MCP/RAG SPI+内置实现）约 10,000–13,000 行 Go；P5 扩展（仓储后端/加载器/talents/sandbox/harness/loop）按需追加，全量对齐约 25,000 行级。分期与验收见 07-migration-plan.md。

1. solon-ai 是什么 ​

solon-ai 是 Solon 生态的 Java LLM 应用框架（自述 "Java LLM(tool, skill) & RAG ... framework"），覆盖从底层模型调用到上层智能体编排的完整链路：

能力域说明solon-ai 对应模块
聊天模型统一 ChatModel API + 5 厂商方言（OpenAI/Anthropic/Gemini/Ollama/Dashscope），call/stream 双路径，30 种流式事件solon-ai-core + solon-ai-llm-dialects
工具调用FunctionTool + JSON Schema 自动生成 + @ToolMapping 反射绑定 + autoToolCall 递归solon-ai-core
智能体Simple（单轮）/ ReAct（推理-行动循环）/ Team（多智能体协作，8 种协议拓扑）solon-ai-agent（构建于 solon-flow）
AI 流编排Dify 式 YAML 低代码编排，AI 能力封装为 flow 节点组件solon-ai-flow
MCPModel Context Protocol 服务端 + 客户端（stdio/SSE/Streamable HTTP），MCP 工具直接并入函数调用mcp-core + solon-ai-mcp
RAG文档加载（7 格式）/ 切分（含语义切分）/ 向量仓储（14 后端）/ 网络搜索（3 家）solon-ai-core SPI + 三件套目录
能力包Talents：cli/code/file/web/memory/lsp/mount 等 18 个「工具+指令+准入」包solon-ai-talents
高级编排Harness（Claude-Code 式编码代理容器）/ Loop（持久化可验证任务循环引擎）solon-ai-harness / solon-ai-loop
沙箱Claude Code sandbox-runtime 的 Java 移植（文件/网络/进程隔离）solon-ai-sandbox
UI 流协议Vercel AI SDK / AG-UI 两种前端流式协议适配solon-ai-ui-*
编辑器协议ACP（Agent Client Protocol，Zed 系）acp-* + solon-ai-acp

Java 8 风格代码（无 sealed/record/虚拟线程）；现代异步全靠 Project Reactor（solon-rx 传递引入）、CompletableFuture 与裸线程。HTTP 客户端统一走 org.noear.solon.net.http.HttpUtils（Solon 自家阻塞式客户端 SPI，不是 okhttp 也不是 nami 的对应物）。

1.2 与 solon-flow 的耦合面（aifei-go 已解决的部分） ​

solon-ai 对 solon-flow 的依赖集中在 solon-ai-agent 与 solon-ai-flow，grep 核实的完整 import 集合为：Graph, GraphSpec, NodeSpec, LinkSpec, Node, Link, NodeType, FlowEngine, FlowContext, FlowContextInternal, TaskComponent, NamedTaskComponent, Evaluation, FlowDriver, FlowOptions, FlowInterceptor, NodeRecord, Container, ConditionComponent。具体接缝：

  1. Agent 接口 extends NamedTaskComponent —— 每个智能体就是一个 flow 任务节点（name() + run(FlowContext, Node)），可直接丢进图里当节点用。
  2. TeamAgent = 图 + 引擎：FlowEngine.newInstance(true) + Graph.create(traceKey, spec -> protocol.buildGraph(spec))，执行即 flowEngine.eval(graph, -1, context, flowOptions)（-1 = 步数不限）。
  3. 协议（Protocol）= 拓扑构建器：spec.addStart(...) / spec.addActivity(agent) / spec.addExclusive(supervisorTask) / ns.linkAdd(target, l -> l.when(cond))，when 是基于 FlowContext 状态的动态路由边。
  4. ReActAgent 不建图：手写 while(true) 的 reason/action 循环，FlowContext 纯作共享黑板（get/put/with）。
  5. solon-ai-flow 组件 = TaskComponent：run(FlowContext, Node)，数据走 FlowContext.vars()，节点事件走 context.eventBus().send(...)。
  6. 一处内部 API 依赖：AgentSession 向下转型 FlowContextInternal（实现 pending/stop）——Go 侧无需此类转换（见 03 第 6 节）。

Go 侧 ./flow 已逐字对应上述概念（flow.NamedTaskComponent = TaskComponent + Name() + Title()，flow.Create(id, func(*GraphSpec))，Engine.Eval/EvalWithSteps，Context.Stop()/With/EventBus()，Evaluation 默认 enjoy），因此这 6 条接缝全部自然落地；唯一缺口是 Node.attachment 公有缓存字段（solon-ai-flow 用它缓存按节点 meta 构建的模型实例），建议作为向后兼容增量补进 flow（见 03 第 7 节）。

2.2 不迁 / 缓迁（明确排除或推迟，供审核取舍） ​

#项目处置原因
Asolon-ai-anp不迁空占位（README 仅「敬请期待」），无实现可迁。
Bsolon-ai 聚合 starter / solon-ai-talents 聚合包不迁Java 侧即无 src/main（纯依赖聚合 + 测试示例）；Go 的包级按需 import 天然覆盖其作用。
CACP 全家（acp-core/annotations/agent-support/solon-ai-acp）缓迁（P5 之后按需，架构预留 ./acp 目录位）① 编辑器（Zed 系）场景，与服务端 AI 应用主线关联弱；② 仓库内自标 @UnstableAcpApi、承诺随时破坏兼容；③ 体量 20.8K 行且与 MCP 的 JSON-RPC 层同构——真需要时 MCP 层可大量复用，边际成本可控。
Dsolon-ai-harness / solon-ai-loop缓迁（P5，契约先立）依赖 talents 矩阵（cli/code/lsp/memory/mount…）与 sandbox，是「全家桶最后一层」；先把 P0–P4 打牢，harness/loop 作为纯增量随时可加（06 立其契约骨架）。
EGraalVM AOT / META-INF/solon 自动装配不迁Go 静态编译即原生；Solon Plugin SPI → aifei.Plugin 命令式装配（既有惯例）。
FReactor 背压/操作符语义以 Go 惯用法替换Flux 的操作符代数（takeUntil/reduce/concatWith…）不逐个复刻；保留事件不变量（这是真正的契约），操作符能力由调用方在 channel/回调上自行组合（02 第 5 节给出映射表）。
Gredisx 直连的 Redis 会话/仓储收口到 ./plugins/cache 通道本仓库既有哲学：Redis 能力走 cache 插件（jetcache-go/go-redis），不为 ai 单独引入第二套 Redis 客户端（flow 迁移处理 RedisStateRepository 时同款决策）。
Hsolon-ai-sandbox 的 Windows 后端（WFP/srt-win.exe）P5 仅 macOS/LinuxWindows 沙箱依赖外部 exe 与 WFP 驱动，无法自测；先覆盖 darwin（Seatbelt）+ linux（bubblewrap），Windows 留接口。
IPDF/PPT/Word/Excel 解析的逐格式对齐P5 分批，先 text/markdown/htmlGo 生态解析库弱于 Java（POI/Tika/PDFBox 无等价物）；P4 先落零依赖与轻量格式，重格式按 plugins/ai/ragloader 逐个引入（pdfcpu/xuri/excelize/goquery 等），TEST.md 矩阵逐项补。
J官方 MCP Go SDK 包装方案否决（保留为备选）modelcontextprotocol/go-sdk 尚未 1.0、依赖面不受控；本仓库 dami/flow/nami 均为原生忠实移植，MCP 协议本身规范清晰（JSON-RPC + 三种传输），自研约 2.5K 行即可覆盖（04 论证）。若用户偏好官方 SDK，可改为 plugins/mcp 包装——决策 D6 留档。

结论：P0–P4 迁完后，aifei-go 拥有「聊天模型 + 方言 + 流式 + 智能体（含多智能体协议）+ AI 流编排 + MCP 双端 + RAG 全 SPI + 内置实现 + 装配」的完整 AI 框架层，对应 solon-ai 的主干与最高频使用面；P5 及之后按真实需求解锁长尾（仓储后端矩阵、talents、sandbox、harness/loop、ACP）。

4. 模块地图与依赖 ​

4.1 在 aifei-go 工作区中的位置 ​

依赖方向严格单向：ai 不依赖 flow（编排能力隔离在 ai/agent、ai/flow 两个独立模块）；mcp 不依赖 ai（可独立作纯 MCP 工具服务）；桥接单向发生在 ai 的子包 ai/mcp（import ./mcp）。

6. 关键设计决策速览（各篇展开论证） ​

#决策结论详述
D1流式 API 形态回调 Sink 为主契约（Stream(ctx, func(*ChatEvent) error) error），channel 适配器（StreamChan(ctx)）为辅；事件不变量原样保留02 第 4 节
D2HTTP 层归属./ai 自带轻量 HTTP+SSE 缝（httpx，可注入 *http.Client）；不改 nami（Channel.Call 请求/响应形状 + 整包缓冲 + 30s 总超时不适配长流）；后续若需要可另立 nami/channel/sse 扩展，与本设计正交02 第 3 节
D3方言事件先行契约沿用 v4.1 设计：方言不返回结果、只 ctx.Emit(ChatEvent)；call 与 stream、全部厂商统一走同一条事件管线再聚合。这是 solon-ai 4.1 最重要的架构资产，原样保留02 第 6 节
D4反射工具绑定@ToolMapping → ai.RegisterTools(providerStruct)：reflect 扫描导出方法 + 参数 struct tag（param:"名称,required" desc:"..."）生成 JSON Schema；主路径仍是显式 ai.NewTool(...) 链式定义（server.Register/dami Lpc 同型先例）02 第 7 节
D5CRTP 泛型链消解ModelOptionsAmend<T,X> 家族 → 每层一个具体 Options 类型（ai.ChatOptions/agent.ReActOptions/agent.TeamOptions）+ 链式 setter + Raw map[string]any 逃生舱；Agent<Req,Resp> → 最小 agent.Agent 接口（flow 集成）+ 各具体类型的 Request/Response01 第 4 节
D6MCP 自研 vs 官方 SDK自研（./mcp，零外部依赖，约 2.5K 行覆盖协议+传输+双端）；理由：仓库自包含哲学 + 官方 Go SDK 未 1.0。备选（包装官方 SDK 为 plugins/mcp）留档04 第 2 节
D7AgentSession 的 FlowContextInternal 依赖Go 侧 flow.Context 即我方接口：pending 语义直接用 Context.Stop() + 会话内标志实现，无需任何 flow 内部 API；快照 = Context.ToJSON()（已有）03 第 6 节
D8node.attachment 缓存已定稿（2026-10-08 审核，方案 A）：为 flow.Node 增加向后兼容的附件缓存 Attachment/SetAttachment（并发安全，序列化忽略），对齐 dataisolate 给 db 加 5 项增量的先例；组件内 sync.Map 的方案 B 降为文档备选03 第 7 节
D9options 形态Java 的全 Map<String,Object> options（弱类型字符串键）→ Go 强类型 Options struct（常用字段显式）+ Raw map[string]any（厂商逃生舱）；方言的 PrepareOutputFormatOptions 仍可读写 Raw02 第 8 节
D10dual 事件层ChatEvent（30 型）与 AgentEvent（~20 类）保持两层分离（Java 同构）；映射代码集中在各 agent 的 ReasonTask/转发处，不散落03 第 5 节
D11取消模型Thread.interrupt → context.Context 贯穿方言 HTTP、工具执行、智能体循环、MCP 会话；SSE 读取尊重 ctx（http.NewRequestWithContext）01 第 3 节
D12协议状态袋AssistantMessage.protocolStates（Anthropic 思考签名、OpenAI snapshot 态）→ Go 显式 ProtocolStates map[string]any，随消息序列化存活于工具循环02 第 2 节

7. 可行性结论 ​

  • 可迁：solon-ai 主干（chat/方言/流式/工具/agent/flow 组件/MCP/RAG SPI）在 Go 中可达语义等价；最重的前置依赖（solon-flow）已经以 ./flow 存在且 API 逐字对应，这是本次迁移相比「从零迁 solon-ai」最大的红利。
  • 语言鸿沟全部有解：Reactor → ctx + Sink/channel（保不变量）；反射注解 → reflect + struct tag（仓库已有先例）；CRTP → 具体类型；双 JSON 栈 → ./json；Redis → cache 插件。
  • 收益：aifei-go 补齐 AI 应用层后，「Just Service + 流程编排 + 智能体 + 工具协议 + RAG」形成闭环；agent 与 flow 同源（都坐在 ./flow 上），与 Java 侧架构演进方向一致。
  • 风险：①流式语义保真——SSE 解析边界（CRLF/[DONE]/多 choice snapshot 归一化）与事件不变量必须以对照测试固化（Java 侧测试用例直接搬译）；②方言矩阵长尾——5 家厂商 ×（chat/embedding/rerank/generate）组合多，P0 只保 openai/ollama 全绿，其余渐进（07 分期细化）；③Go 解析生态缺口——pdf/ppt/word 无 Tika 级等价物，P5 分批引入并降级预期；④MCP 协议版本追踪——自研需跟随 spec 演进（锁定 2025-06-18 为基线，2025-11-25 的 Form/Url elicitation 标记为扩展位）。
  • 工作量预估（含与实现 1:1 的测试）：
